# Python local service boundaries

First follow the root `AGENT.md`.

- This directory is an independent Python package; it does not import frontend implementation or depend on native AXIS.
- v1 `health` preserves the historical diagnostic format; v2 provides a single-writer control session, status, commands, and isolated preview. `machine.status` lets unattached local observers read fresh state without obtaining control or renewing jogging leases. Never fabricate feedback or start LinuxCNC.
- Public entry points are `betterlinuxcnc_service` (`main`, `serve`, and `python -m betterlinuxcnc_service`), `bettercnc_controller.Controller` (including restricted CAM job interfaces `start_received`/`received_status`, `start_homing`/`homing_status`, and `cancel_cam`), `bettercnc_controller.StatusReader`, `bettercnc_preview.parse_program`, and the preview CLI. Underscore-prefixed files are private.
- service depends only on public controller/preview entry points. controller owns machine rules, file writes, and LinuxCNC command/error channels; preview invokes LinuxCNC's `gcode` extension in a separate process without duplicating the interpreter. Neither may depend back on transport or Qt.
- Serialize all Controller calls on one worker thread. CAM jobs belong to the service and may reuse the desktop's current Controller. Closing an upload or desktop connection does not revoke accepted CAM jobs. Service shutdown/state loss cancels unsent steps and records unknown without aborting running programs or replaying automatically. Jogging requires a session lease; loss of contact stops that session's jogging and cancels unsent steps. Never automatically retry an unknown outcome. Machine file writes require fresh state validation, not trust in client capabilities.
- `StatusReader` owns only `linuxcnc.stat` and is called serially with Controller on the service worker thread; it must not create command/error channels. The CAM network service moved to `../platform/cam-link/`; this package no longer provides `bettercnc_cam_link` or a Python network startup entry point.
- The Rust service calls `machine.status`, `cam.job.start/status/cancel`, `cam.home.start/status/cancel`, `cam.workflow.start`, and `cam.jog.start/keepalive/stop` through the public Unix protocol. The controller service retains the single Controller, interlocks, persistent job state, and independent jogging leases without depending on Rust internals. See `../../docs/cam-link-protocol.md`.
- Test behavior through public objects, installed CLI, and sockets. Vendor modules, clocks, and preview-process factories may be injected; do not import private files. Real gcode tests interpret temporary programs only and never start simulators or hardware.
- Connectivity checks use unattached `machine.status`; diagnostics must not acquire the existing GUI's control, read the error channel, or renew jogging leases. Preserve feedback that the socket is reachable but LinuxCNC is offline; service readiness is not core readiness. External-interface integration tests inject the same vendor into both Controller and StatusReader; replacing only the command interface makes observers read the real or missing LinuxCNC module.
- After changes, run Ruff checks, formatting checks, package builds, and `unittest`; protocol changes also require Rust cross-process integration tests.
- Dedicated-appliance homing separately requires verified switch inputs, mapping of motor channels to physical axes, and motor polarity. Missing or non-YES `MOTOR_MAPPING_VERIFIED` or `MOTOR_DIRECTIONS_VERIFIED` rejects homing and coordinated motion requiring homing. Preparation tools must not automatically claim physical motor acceptance. Public `homeAllUnavailableReason` accompanies capability information with the disabled reason; the GUI displays it without relaxing conditions.

- The user requires one-click LAN connection: without a token, `session.auth` uses an empty-parameter handshake; when a token is supplied, continue validating it. Do not automatically fall back or remove machine interlocks, file hashes, or jogging leases.
