## Technology and system boundaries

- Target runtime: Debian 13 and Intel integrated graphics. Target Python 3.13.5, PySide6 6.8.2.1, a real-time kernel, and X11 `DISPLAY=:0` have been verified. CPU model, actual GPU/Qt rendering backend, installed LinuxCNC version, and other scaling combinations still require verification as needed; do not infer the installed version from repository VERSION.
- Native desktop: Qt 6.8+, Qt Quick/QML, PySide6, Python 3.11+, and CMake. C++17 is used only for the Qt Quick Test launcher. The Web application has been deleted; QML/Python responsibilities and existing control implementation are unchanged.
- The control chain is QML → PySide6 QObject → Unix domain socket → independent Python controller service → LinuxCNC. The desktop must not import LinuxCNC directly. See the [Tauri architecture record](docs/tauri-local-control-architecture.md) for historical Vue/Tauri decisions. Do not build an HTTP/WebSocket control gateway; see the [local control protocol](docs/local-control-protocol.md) for v2.
- LinuxCNC itself owns G-code interpretation, interpolation, motion planning, real-time threads, and HAL. QML, PySide6, Rust, and the Python controller service must not perform real-time servo work. The desktop adapter owns the window and communication bridge; the service owns machine operation rules. Do not duplicate control logic.
- The controller service owns the application's sole command-write entry point and sole error-channel reader. Write access from other UIs/HALUI still needs coordination; cancel subsequent command steps if another writer advances the acknowledgement serial number. Preview runs in a separate process using LinuxCNC's `gcode` extension.
- Neither the service nor the desktop supervises or starts LinuxCNC; do not assume LinuxCNC keeps running after `DISPLAY` exits. On disconnect, cancel unsent commands and stop this session's jogging without automatically aborting a running program. Do not replay commands on reconnect.
- v1 `health` retains its historical diagnostic format and cannot establish machine connectivity; real state comes only from v2 sessions. Offline coordinates display as unknown. Test fixtures must never enter the production data flow.

## Module boundaries

`app/launcher/` is an independent orchestration entry point using only the Python standard library. It reads `/etc/betterlinuxcnc/launcher.json` by default. Installed `betterlinuxcnc-launch --kiosk-session` maintains the dedicated X11 session and starts the controller service, native `linuxcnc <ini>`, and CAM integration in order through systemd user services. Readiness probes query only public v2 `machine.status` without obtaining a control session. Module supervision does not replay commands; restarting the native core requires confirmation that its old process group and native lock have been released. `BETTERCNC_PROJECT_DIR` remains a build interface, but official appliance releases use fixed `/etc/betterlinuxcnc` to match root updater configuration constraints. Packages do not import or overwrite machine configuration.

`tools/appliance/` owns fixed account/directory provisioning, explicit machine migration, and maintenance interfaces. The DEB's sole fixed `postinst` calls `provision`, which idempotently creates or validates dedicated accounts and directories. It does not set passwords, import machine configuration, activate login policy, or start services. Explicit `prepare` copies existing machine configuration into the system directory while preserving originals; only the migrated copy has runtime data paths adjusted and external editors/filters disabled. `activate` writes dedicated login policy; installation, the GUI, and ordinary updates must not invoke it automatically. The operating account `linuxcnc` and read-only SSH maintenance account `cnc-maint` are separate; neither receives generic sudo/root shell access. Root is used only for explicit configuration and the fixed updater service. Passwords are supplied only through non-echoed stdin, never source, command arguments, packages, logs, or documentation.

Fixed `betterlinuxcnc-appliance backup` runs only as root and accepts no arbitrary input/output paths. It saves `/etc/betterlinuxcnc`, mutable machine data such as parameters/tool tables under `/var/lib/betterlinuxcnc/machine`, and fixed host policies managed by the tool into root-private `/var/lib/betterlinuxcnc/recovery/snapshots`, recording SHA-256, application version, and time. Older snapshots are removed only after a new snapshot is successfully created and verified; retain the latest three. Do not back up large program libraries, inbox contents, caches, or account passwords, and do not restore automatically. Snapshots on the same disk cannot survive disk failure and do not replace independent backups.

See [app/desktop/AGENTS.md](app/desktop/AGENTS.md) for Qt directories and dependencies: organize modules as `BetterCnc.<Capability>` and expose types through `qmldir`; compose components through public state and signals. Rust `src/lib.rs` is the public entry point; communication internals remain private. Follow `tools/diagnostics/AGENTS.md`, `app/platform/cam-link/AGENTS.md`, and `app/platform/updater/AGENTS.md`. Cross-module and application-layer imports may use only public entry points. Dependency cycles, reverse dependencies, and production references to test fixtures are forbidden.

Project-owned applications are consolidated under `app/` by responsibility. `desktop`, `controller`, and `launcher` retain the Python/Qt interface, machine-control, and orchestration roles. `app/platform/` groups Rust platform capabilities: `cam-link`, `updater`, and `mesa-update`. Each platform module retains its own public entry points, build manifest, process lifecycle, and privilege boundary; the grouping is not a shared privileged service. Future configuration management belongs in this layer once its interface is defined. Implementation languages belong in module build manifests, not directory names. The independent v1 compatibility diagnostics library lives in `tools/diagnostics/`. `src/` retains native LinuxCNC source and its build system; `docs/`, `tests/`, `configs/`, and upstream resource directories retain their roles. Organize module internals by function, device, or bus; add platform/CPU subdirectories only for actual implementation differences. See the [module map](docs/module-map.md) for directories and public entry points.

The root `CMakeLists.txt` combines product application builds, tests, installation, and packaging; each application module owns its installed content. It neither builds nor installs the native LinuxCNC core, which is still built centrally from `src/`. `src/hal/`, `src/hal/drivers/`, and `src/hal/user_comps/` are physical directories; compatibility links introduced by language-based migration have been removed. Existing coupling between HAL private headers and its runtime remains a legacy boundary recorded in module AGENTS files; directory cleanup must not expand public APIs.

Official DEBs build fixed `zhulong_homing.so` separately with `BETTERCNC_BUILD_MESA_HOMING=ON`; `tools/mesa-homing/` owns the adapter. It generates only headers/halcompile from the current native 2.9.10 source, not the complete core. Vendor input is pinned by `vendor/cnc-mesa/SOURCE.json`; do not modify snapshot files. The packaged module supports only upstream core version 2.9.10. Explicit `prepare` must verify core/development package versions, headers, and module hashes; package CI uses Debian 2.9.4 only for install lifecycle checks and never loads the module. On 2026-10-26, the user supplied measured X/Y/Z total travel of 420/275/90 mm. Explicit `--zhulong-homing-travel-mm 420 275 90 --zhulong-xyz-only` can merge complete homing configuration into an existing configuration copy. For unknown travel, use mutually exclusive `--zhulong-inputs-only`. The user confirmed this machine has only XYZ; the three-axis option strictly removes the reviewed reserved ABC configuration. Six-axis configuration without that option retains all real homing interlocks. Installation and updates must never trigger HOME automatically. ELF checks, public API harnesses, and HDL simulation do not constitute machine motion acceptance.

Explicit adapters alone own external network, file, process, and platform interfaces. Qt `bettercnc.desktop` exposes read-only state and actions to QML; `bettercnc.session` owns the socket. Service `bettercnc_controller` owns control rules and machine file writes; `bettercnc_preview` owns isolated interpretation. Independent `tools/diagnostics` owns v1 diagnostic transport and is not embedded in the Qt control chain. UI components must not directly access LinuxCNC, HAL, sockets, HTTP, or WebSocket.

The protocol must distinguish joint/axis, machine/work coordinates, commanded/actual positions, and angular/linear units. Command states “accepted,” “sent,” “completed,” and “outcome unknown” must remain distinct. Reconnection must never replay motion, MDI, or spindle commands. Software emergency-stop UI does not replace physical safety circuits. Automated regressions do not start simulators or machines; use vendor-interface substitutes, real Unix sockets, and the LinuxCNC `gcode` extension for file-only interpretation.
